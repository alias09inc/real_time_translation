# リサーチエージェント・パイプライン概要

> このファイルは「パイプラインの仕組み」を説明する常設ドキュメントです。
> 各サイクルの実験結果は `research_agent/reports/YYYYMMDD_cycle<N>_report.md`
> の方に書かれます。仕組み自体（状態遷移・予算・承認ルールなど）が変わった
> ときだけ、このファイルを更新します。

最終更新: 2026-09-08（構築時点）

## 1. 目的

このリポジトリ（Zoom/YouTube英→日リアルタイム字幕翻訳システム）について、
文献（同時通訳・ストリーミング翻訳研究）に基づいた改善仮説を立て、実際に
実験で検証し、結果をレポートする、というサイクルを人手を介さず自動で回す
ためのエージェント基盤です。

## 2. 状態遷移（ステートマシン）

```
SEARCH_PAPERS        論文・記事を検索する
   ↓
EXTRACT_PAPERS       見つけた論文の中身を取得する
   ↓
READ_PAPERS          要約・要点を抽出し、既存実験と重複しないか確認
   ↓
GENERATE_HYPOTHESES  検証可能な仮説を1〜3件作る
   ↓
HUMAN_APPROVAL        予算内かチェックし、自動承認 or 人間に確認依頼
   ↓ (承認待ちなら WAITING_APPROVAL で一旦停止)
RUN_EXPERIMENTS       既存の実験ランナー（youtube_segment等）で実験を実行
   ↓
ANALYZE_RESULTS       結果を過去のベースラインと比較・評価
   ↓
WRITE_REPORT          日本語でレポートを書く（今読んでいるこのファイルの隣）
   ↓
REFLECT               自己反省・自己改善（後述）
   ↓
SEARCH_PAPERS へ戻る（サイクル+1）、または GENERATE_HYPOTHESES へ直接戻る
```

現在地は常に `research_agent/state/pipeline_state.json` の
`current_state` に記録されています。

## 3. 状態管理・コンテキスト管理の仕組み

このエージェントは「1回のセッションで全部やりきる」設計ではなく、**毎回
記憶を持たない新しいセッションが起動されても、ファイルを読むだけで続きから
再開できる**ように作ってあります（コンテキスト切れやセッション終了に強い
設計）。

| ファイル | 役割 |
| --- | --- |
| `research_agent/PLAYBOOK.md` | 各状態で何をすべきかの手順書。新しいセッションが最初に読む「取扱説明書」 |
| `research_agent/orchestrator.py` | 状態遷移の正当性チェックと予算管理だけを行う、依存ライブラリ無しの小さなPythonスクリプト |
| `research_agent/state/pipeline_state.json` | 現在の状態・サイクル番号・履歴 |
| `research_agent/state/papers.json` | 見つけた論文・要約・キーとなる知見 |
| `research_agent/state/hypotheses.json` | 仮説の一覧（提案中／承認済み／実験中／検証済み） |
| `research_agent/state/budget.json` | API予算の残高管理 |
| `research_agent/state/reflections.md` | 自己反省ログ（英語、内部メモ） |
| `research_agent/reports/*.md` | 人間向けレポート（日本語） |

「内容そのもの」（論文の要約や仮説の文章）はエージェント（Claude）が直接
JSON/Markdownファイルを読み書きして管理します。`orchestrator.py` は
「状態遷移が正しい順番か」「予算を超えていないか」という**機械的に判定
できる部分だけ**を担当します。判断が要る部分は毎回Claude自身が考える、
という役割分担です。

## 4. 予算と承認ゲート

自律実行中に無制限にAPIを叩かないよう、下記のルールを設けています
（`research_agent/state/budget.json`）。

- 1日の上限: **$7**
- 1バッチ（1回の実験実施判断）の上限: **$3**
- 既存のYouTubeクリップ（`experiments/refs/` 配下、既に使用実績があり
  利用規約の確認も済んでいるもの）の再利用のみ許可。新規動画のダウンロード
  は自動承認の対象外。

仮説がこの条件を満たす場合は「自動承認」され、そのまま実験に進みます。
条件を超える場合（予算超過、新しい動画が必要、本番パイプラインへの
直接変更など）は `WAITING_APPROVAL` 状態で止まり、
`research_agent/state/pending_approval.json` に理由と見積コストを書いて
人間（あなた）に判断を仰ぎます。つまり **「小さい・安い・既存データの
範囲内」の実験は完全自動で回り、「大きい・高い・新規データが要る」判断
だけがあなたのところに上がってくる**、という設計です。

## 5. 自己反省・自己改善（self-reflection）

`REFLECT` 状態で、毎サイクル以下を自問し `reflections.md` に追記します。

1. 今回のサイクルで何がうまくいった／いかなかったか
2. 仮説の立て方は妥当だったか（野心的すぎる／慎重すぎる／過去の実験と
   重複していないか）
3. 予算ポリシーは適切か（変更が必要なら、勝手に変えずに次のレポートで
   人間に提案する）
4. **手順書（PLAYBOOK.md）自体を直すべきか** — 同じ勘違いや手戻りを
   繰り返しているなら、エージェント自身がPLAYBOOK.mdを編集して次回以降
   同じ失敗をしないようにします。これが「自己改善」の実体です
   （承認ゲートや予算チェックの仕組み自体は、人間の明示的な指示なしに
   削除・弱体化してはいけない、というガードレールを設けています）。

## 6. 自律実行（あなたのラップトップが閉じていても動く仕組み）

このエージェントは**クラウド上のスケジュール実行（cron）**として動きます。
つまりあなたのラップトップ上のプロセスではなく、Anthropicのクラウド側で
定期的に新しいセッションが起動し、上記の状態遷移を1ステップ以上進めて
コミットする、という形です。ラップトップの電源やスリープ状態には一切
依存しません。スケジュール自体は `/schedule` の仕組みで作成・確認・
停止ができます。

## 7. 実験実行と記録

実験の実行自体は既存の `real-time-translation-exp-youtube` /
`real-time-translation-exp-video` ランナーをそのまま使います。仮説の
`required_changes` に応じて、`src/real_time_translation/` 側に小さな
実験用トグル（環境変数で有効化、デフォルトは現状の挙動を維持）を追加
することもあります（例: サイクル2の `MASKING_HOLDBACK_WORDS`）。
いずれの場合も既存のCLAUDE.mdの実験記録ルール（`experiments/YYYYMMDD_<実験名>.json`
作成 + `results.csv` 追記 + git commit）にそのまま従います。リサーチ
エージェント側の状態ファイルも同じタイミングでコミットするようにしています。

**サンドボックス環境特有の注意（サイクル2で判明）**: クラウド実行環境
（`Claude Code on the web` 等）のネットワーク egress プロキシが、
使用する外部ホストごとに個別に許可/拒否を設定していることがあります。
サイクル2の時点では `generativelanguage.googleapis.com`（Gemini）は
疎通するが `api.deepgram.com`（ASR）は組織ポリシーで拒否される、
という非対称な状態が確認されました。`RUN_EXPERIMENTS` 状態の環境
チェックで単に「キーが設定されているか」だけでなく、実際に疎通するか
（`curl` で直接叩いてHTTPステータスを見る）も確認すると、原因の切り分けが
速くなります。

**続報（サイクル3で判明）**: ネットワーク許可状態はセッションをまたぐと
変わり得ます。サイクル3では `api.deepgram.com` の REST エンドポイント
（`/v1/projects`）は 200 で通るようになっていましたが、実験ランナーが
実際に使う **Listen 用 WebSocket**（`wss://api.deepgram.com/v1/listen`）
は依然 403 で拒否されました。つまり「同じホストの REST が通る」ことは
「その上のストリーミング/WebSocketも通る」ことを保証しません。
`PLAYBOOK.md` の環境チェックには、実際に Listen WebSocket への接続を
試すコードを追加済みです。また `uv sync`/`uv run` は全 extras
（`zoom` の `rtms`、testpypi 限定）をまとめて解決しようとして失敗する
ことがあるため、実験用の依存関係だけが必要な場合は
`uv pip install -e ".[experiments]"`（venv を手動で作って使う）の方が
安全です。

## 8. 今のところ分かっていること（初回サイクルの立ち上げ時点）

- 既存の実験ログ（`experiments/*.json`）には、ASRの中間結果・翻訳の
  部分結果がタイムスタンプ付きで全て記録されている一方、**「字幕が
  どれだけ書き換わったか（flicker/normalized erasure）」を測る指標は
  一つも存在しない**ことが分かりました。これは提供いただいたサーベイが
  指摘する「オフライン評価は revision/flicker を完全に見落とす」という
  問題そのものです。
- そこで最初の仮説として、**追加のAPI呼び出しゼロ**（既存ログを読むだけ）
  でこの指標を実装・計測することにしました。詳細は最初のサイクルレポート
  （`research_agent/reports/`配下の日付付きファイル）を参照してください。
- **続報（サイクル4）**: 最初のNE実装（`group_translation()`）は
  1回のバッチ呼び出し単位（`(asr_start_time, asr_end_time)`）でしか
  グルーピングしておらず、「1発話が複数バッチにまたがって
  ゼロから再翻訳される」ケースの書き換えを見落としていました。
  発話単位（`is_utterance_end` を使った逐次ヒューリスティック）で
  グルーピングし直す `group_translation_by_utterance()` を追加した
  ところ、複数バッチにまたがる発話（全体の約6.2%）では平均NE約1.47
  （＝画面上の訳文がほぼ丸ごと書き換わる）という、当初の「翻訳の
  ちらつきはほぼ無い」という結論を覆す結果が出ました。詳細は
  `research_agent/reports/20260908_cycle4_report.md` を参照してください。
  教訓: 集計指標は「何を1単位としてグルーピングしているか」次第で
  結論が大きく変わり得るため、新しい指標を実装した際は集計の粒度が
  測りたい現象と一致しているかを確認することが重要です。
